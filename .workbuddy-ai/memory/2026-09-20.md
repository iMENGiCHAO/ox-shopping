## 一、🔴 重大通道修正：**Playwright 能直接访问 shop.x.com**

此前（2026-09-18/19）记录的结论是「沙箱封 x.com，只剩 thum.io 像素通道」。
**这个结论对浏览器通道不成立**，必须修正：

| 通道 | 结果 |
| --- | --- |
| Node `fetch` → `shop.x.com` | ❌ `ECONNRESET` |
| Node `fetch` → `r.jina.ai` | ❌ `UND_ERR_CONNECT_TIMEOUT` |
| `WebFetch` → `r.jina.ai/<url>` | ✅ 可用（拿到 DOM 文本，但被转成 markdown） |
| **Playwright（真实 Chromium）→ `shop.x.com`** | ✅ **200，标题 `Official SpaceXAI Shop`** |

实测命令：
```js
const {createRequire} = require("node:module");
const req = createRequire("/Volumes/Time Machine/DeepSeek/ecommerce/package.json");
const { chromium } = req("@playwright/test");
const b = await chromium.launch();
const p = await b.newPage();
await p.goto("https://shop.x.com/", { waitUntil: "domcontentloaded" }); // → 200
```

**这意味着可以直接对原站做「交互 + 几何 + 截图」取证**，不必再受这些限制：
- thum.io 的图像 0.5× 缩放、高度固定 600、无法交互
- r.jina.ai 只有文本、拿不到 CSS 与几何

**能取到但过去取不到的东西**：点开页头搜索 → 输入 → **联想面板的真实形态**；

## 九、🔴 更正一处我自己的误判：`In stock only` **是开关，不是复选框**

第 §三 节里我据文本代理（r.jina.ai）的 markdown `- [x] In stock only`
推断「原站是复选框、本地用 Switch 是错的」。**实测推翻**：

```
checkbox: { tag: "input", cls: "switch", w: 36, h: 16, pad: "3px",
            bg: "rgba(255,255,255,0.2)", display: "grid" }
```

原站元素是 **`input.switch`，36×16** —— 就是一个**开关**，与本地 `Switch` 一致。
**教训**：markdown 代理会把开关渲染成 `- [x]`，**不能据它判断控件类型**；
控件类型必须看真实 DOM 的 `tagName` + `className` + 尺寸。

## 十一、🔴 全站容器内边距：原站是**三级曲线**，本地 700–999 宽了 16px

用 Playwright 对原站多页逐视口实测（首页 / PLP / 搜索 / FAQ），结论**统一**：

| 视口 | 内容页（FAQ 等） | 商品网格页（首页 / PLP / 搜索） |
| --- | --- | --- |
| **<700px** | 20px | **10px** |
| **700–999px** | **32px** | **32px** |
| **≥1000px** | 48px | 48px |

实测数据（内容区左缘 x）：
- 首页 / PLP / 搜索的网格：375/500/699 → **10**；700/767/999 → **32**；1000/1216 → **48**
- FAQ 正文列：375/500/699 → **20**；700 → 32（再往上列被居中，x 随视口增大）

**本地错在两处**：
1. `--shell-pad` 是「20px，≥700px 起 48px」→ **700–999 区间整站宽 16px**
2. `tailwind.config.ts` 的 `container.padding` 是「20 / ≥640 起 48」→ 在 640–699 给出 48px
   （原站该区间是 20px），而且**与 `.shell` 的断点还不一致**（640 vs 700）

### 修复（只动店面，后台不受影响）

`data-shop-root` 只出现在 `(shop)/layout.tsx` 与 `(checkout)/layout.tsx`，后台没有 →
用它把改动限定在店面：

```css
@media (min-width: 700px) and (max-width: 999px) {
  [data-shop-root] { --shell-pad: 2rem; }   /* 32px */
}
[data-shop-root] .container {
  max-width: min(100%, var(--shell-max));
  padding-inline: var(--shell-pad);   /* 与 .shell 统一为单一事实来源 */
}
```

另给 `/search` 页加 `--search-page-pad`（10 / 32 / 48，该页不用 `.shell`/`.container`），
并把页面里的 `px-5 lg:px-12` / `-mx-5 lg:-mx-12` 换成 `px-[var(--search-page-pad)]` /
`-mx-[var(--search-page-pad)]`。

**注意**：`qa:layout` 用的是 1216 视口，该区间两端都是 48px，因此不受影响。

### 途中又踩一个 CSS 令牌坑：`--a: var(--b)` 写在 `:root` 上，元素级覆盖传不进去

`--plp-shell-pad: var(--shell-pad)` 声明在 `:root` → `var()` 在 **`:root` 上就解析完**，
`[data-shop-root] { --shell-pad: 32px }` 这种元素级覆盖**不会回流**。
实测症状很典型：`.shell` 与 `.container` 都正确变成 32px，**只有 `.plp-shell` 仍是 48px**
（首页商品网格就是 `shell plp-shell` 两个类同挂）。
修法：`var()` 直接写在**消费它的规则里**（`.plp-shell { padding-inline: var(--shell-pad) }`）。
**「一部分元素对了、另一部分没对」正是这类间接引用失效的特征。**

| --- | --- | --- | --- |
| 1216 | 1120 | **48px** | **341×406**，首行 y=280，pitch **470** |
| 1395 | — | **48px** | 401 |
| **1400** | — | **60px** | 395 |
| 1440 | 1344 | 60px | 408×473，pitch 537 |

### 🔴 更大的一个错：`--cart-empty-pb` 写死 250px

### ⚠️ 测量口径陷阱：**矮视口才量得到真实页高**

否则会去改一个本来就对的令牌。
