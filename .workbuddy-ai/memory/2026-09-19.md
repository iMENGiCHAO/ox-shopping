## 二、**刷新令牌并发轮换被误判为「重放」→ 用户被强制登出**（本轮最重要的发现）

### 症状（服务器日志实证）

```
同一 userId 在 12 秒内触发 12 次「refresh token 重放，已吊销该用户全部会话」
后台看板随即 401
```

### 根因：并发 ≥3 必然误判

`proxy.ts` 在 access token 失效时对**每一个**请求调用 `rotateSession`，
而一个页面（尤其后台看板）会同时发多个 API 请求，带着**同一个** refresh token 并发到达：

| 请求 | 看到的状态 | 走的分支 |
| --- | --- | --- |
| A | R1 合法未用 | 正常轮换 → R2（标 R1.revokedAt/replacedBy） |
| B | R1 已轮换，R2 未用 → 链未闭合 | 善意重试 → 吊销 R2、签发 R3 |
| C | R1 已轮换，**R2 已被 B 吊销** → 链已闭合 | **判定重放 → 吊销全部会话** ❌ |

### 修法

新增 `ROTATION_REUSE_GRACE_MS = 60_000`：旧 token 在**刚被轮换后的宽限期内**
再次出现，一律按「同一客户端的并发请求 / 响应丢失后的重试」处理。

同时修掉一个**次生隐患**：善意分支原先无条件吊销后继 token。若只是宽限期内的
并发复用（链已闭合），后继很可能已经写进了客户端 Cookie，吊销它会让下一次请求
拿着「已吊销且无后继」的 token **直接命中重放分支** —— 又把人踢下线。
现改为**只在「链未闭合」时**回收后继（此时可确认客户端从未收到它）。

安全性：真正的令牌窃取重放发生在被盗之后（远超数十秒），仍会命中
「链已闭合 **且** 超出宽限期」分支被吊销。与业界通行的 refresh-token
grace period 是同一折中。

### 验证（`scripts/qa/qa-rotate-concurrency.ts`）—— 含反证

测试分两个场景：

- **场景 A（紧并发）**：N=5 个请求同时携带同一个 R1。这条路径原本就靠
  `isChainUnclosed` 兜住了，用于确认没有回归。
- **场景 B（陈旧 Cookie，原缺陷的确定性复现）**：
  1. `rotate(R1) → R2`（R1.replacedBy=R2）
  2. 再次 `rotate(R1) → R3`（善意重试，回收 R2 ⇒ R2 已吊销、**无后继**）
  3. 浏览器 Cookie 里留下的是 **R2**（并发响应覆盖顺序所致）→ 下一次请求带着 R2
     ⇒ 链已闭合 ⇒ 原实现判重放、吊销全部会话

**反证（把宽限期临时置 0 ≈ 旧行为）：**

```
场景 A：成功 5/5   误判重放 0   会话存活 token 5
场景 B：构造完成 R2 已吊销=true R2 无后继=true R3 已签发=true
        携带 R2 请求：误判重放 1   会话存活 token 0
❌ B：陈旧 Cookie 被误判为重放（原缺陷）
❌ B：会话被全部吊销 —— 用户会被强制登出
```

**修复后：两个场景全绿**（见下方实跑）。这条反证证明测试确实能捕捉该缺陷，
而不是「改完刚好也过」。

> 跑这个测试必须加 `NODE_OPTIONS=--conditions=react-server` ——
> `lib/auth/session.ts` 带 `import "server-only"`，该包在默认条件下会主动抛错，
> 只有 react-server 条件才解析到空模块。另外本仓库无 `"type": "module"`，
> tsx 按 CJS 处理 → **不能用顶层 await**，要包一层 `main()`。

## 三之二、改文案引出的两个连带缺陷（**改错误文案后必须全库搜一遍**）

### 1. `e.message.includes("异常登录")` 被我改坏了

`app/api/auth/refresh/route.ts` 原本用**中文子串**判断是否重放：

```ts
if (e instanceof Error && e.message.includes("异常登录")) { logger.warn(...) }
```

我把文案英文化后，这个判断**静默失效**（审计日志不再打印重放拦截）。
根因是**按文案分支**这一反模式。修法：新增专用错误码
`ApiErrorCode` 里的 `"REPLAY_DETECTED"` + `replayDetected()` 工厂，
调用方改判 `e.code === "REPLAY_DETECTED"`。全库已搜过，
没有其它 `message.includes(...)` / `message === ...` 的分支残留。

### 2. `tests/integration/refresh-rotation.test.ts` 编码的是**旧策略**

原文件断言「被吊销且无后继的 token 再次出现 = 真重放 → 吊销全部」。
这正是被生产日志证伪的那条策略。已重写为 4 个用例，把新策略固化下来：

1. 链未闭合的善意重试 → 200
2. **宽限期内的并发复用（4 个并发）→ 全部 200，会话存活**（生产缺陷回归护栏）
3. **超出宽限期 + 链已闭合 → 401 且吊销全部**（安全底线未被放宽掉）
   —— 用「把 `revokedAt` 往前挪 120s」实现，不依赖 fake timers
4. 轮换出的新 token 可正常继续使用（未被宽限期逻辑误伤）

### 集成测试的两个环境事实（写测试前必须知道）

- **集成测试用独立的 `ecommerce_test` 库**（`.env.test` 的 `DATABASE_URL`），

## 八、测试基础设施：两个真实缺陷（本轮修复）

### 1. `shop-flow.test.ts` 60s 超时 = 假失败，不是业务缺陷

隔离运行 **6/6 通过**，但「下单→支付→发票→退款」单条耗时 **53.7s**，
贴着 vitest 默认 `testTimeout: 60000`；全量运行时进程内 DB 争用更大 → 必然超时。
该用例串了十余次往返（建单/扣库存/重复支付/模拟支付/取消拦截/详情/PDF 发票/
申请退款/后台审批），链路长度决定它天然慢。

**修法**：给这一条显式放宽到 `180_000`（`it(name, fn, 180_000)`），
并写明理由。**不要**去调全局 `testTimeout`——那会把真超时也一起放过。

### 2. 库存跨测试轮次单调递减（潜在假失败）

`prisma/seed.ts` 对商品用 `update: {}`（**刻意非破坏**，绝不覆盖人工改过的
价格/库存）→ 商品库存**不会**在每轮测试前重置。
于是 `stock > 10` 这类「挑一个库存够的商品」的写法，早晚会因为前面几轮把库存
跑干而失败，且失败信息（`No Product found`）完全指不到真正原因。

**修法**（`shop-flow` + 新增 `coupon-flow` 均采用）：
挑完商品后把库存**抬到基线**（`stock < 200/500` 才 update）——
只升不降，既不破坏其他用例，也让文件可重复运行。

## 十一、重大发现：硬编码扫描器**谎报 0**（本轮修掉）

`scripts/qa/qa-error-lang.mjs` 报「✅ 0 处」，实际有 **52 处**中文错误文案。

**根因**：旧判据是「构造器名后紧跟引号」——

```js
const re = new RegExp(`${ctor}\\(\\s*(?:\`|")`);   // ❌
```

但 `ApiError` 的签名是 `(status, code, message)`，**文案在第三个参数**。
于是全部 `new ApiError(400, "BAD_REQUEST", "中文")` 都匹配不到，
而这类写法在 `order.service.ts`（订单/退款/库存核心）里恰恰最多。

**这次泄漏里最严重的**：`assertOrderAccess` 的 `无权访问该订单`（403），
被**顾客侧** `/api/orders/[orderNumber]/*`（详情/退款/支付/发票/确认收货/取消）
使用 → 英文站顾客访问他人订单会收到**中文**提示。

**修法**：改为「定位构造器调用 → 平衡括号截取整个实参表 → 在实参里找含 CJK 的
字符串字面量」，覆盖单/双引号、模板串与多行调用。修好后：**17 处真泄漏 + 35 处后台豁免**。

**教训（已写进 skill）**：**一个会谎报 0 的扫描器比没有扫描器更糟**，
因为它制造虚假信心。审计结论必须由「能证明自己会命中」的扫描器给出。

## 十二、修掉一个会让定时任务**永久静默失效**的缺陷

单元测试跑出未处理异常：`TypeError: runScheduledJobs is not a function`
（`src/server/jobs/start.ts:22`）。

**根因**：`lib/prisma.ts` 用 `void import("@/server/jobs/start")` 拉起调度器；
`start.ts` 在**注册时静态捕获**了 `runScheduledJobs`；而
`globalThis.__cronStarted` 守卫保证「只注册一次」。守卫保护的定时器比模块实例
活得久 —— 一旦模块实例被替换（dev HMR、或测试环境按文件重建模块图），
旧定时器持有的就是**上一个实例的导出**，每一跳都抛错，
且因守卫拦着**不会重注册** → 订单超时取消 / Token 清理 / 掉单对账
**全部永久停摆**（正是「超时未支付自动取消」这条商用必守逻辑）。

**修法**：心跳里 `void import("@/server/jobs/scheduler").then(m => m.runScheduledJobs())`，
每跳重新解析模块。频率 60s，走模块缓存，代价可忽略。

**测试侧**：`tests/helpers/setup-env.ts` 设 `CRON_ENABLED=false` ——
测试进程不该起后台调度器（要验证就直接调 `runScheduledJobs()`）。
改完 159/159 通过，且未处理异常消失。

## 十五、定时任务第二个缺陷：选主事务 5s 超时（日志发现）

修完「静态捕获失效」后，把 dev server 拉起来看日志，又抓到一条**级别更高**的问题：

```
Transaction already closed: A commit cannot be executed on an expired transaction.
The timeout for this transaction was 5000 ms, however 6570 ms passed since the start of the transaction.
msg: "[cron] 心跳执行失败"
```

`runScheduledJobs` 把**所有任务**包在 `prisma.$transaction()` 里，用的是 Prisma
**默认 5s** 交互事务超时。但这个事务存在的**唯一**目的是持有
`pg_try_advisory_xact_lock`（事务级咨询锁），所以它的存活时长 = 本轮全部任务耗时。
慢库/外置卷上实测 6.57s → 必然超时：

- 每轮心跳都打错误日志 + `captureMessage` 报监控（噪音告警）；
- **更严重**：事务一死锁就提前释放，而任务可能还在跑 → 多实例下
  **选主失效、会被另一个实例重复执行**。

**修法**：显式给足 `$transaction(fn, { timeout: 5 * 60_000, maxWait: 10_000 })`，
并写明「这个事务的时长由任务耗时决定，默认 5s 是错的」。

**遗留（已在注释里标明，列为后续项）**：`runAllJobs()` 里含 Stripe 网络请求，
也就是**在数据库事务里做网络 I/O** —— 事务时长被外部服务延迟支配，是不推荐的做法。
彻底解法是改用「租约表」（`lockedUntil` 字段 + 条件更新 + 续租）让任务在事务外跑。
当前用超时兜底保证正确性。

**新增 `tests/integration/cron-jobs.test.ts`（7 项）** —— 这条链路**没有任何页面能触发**，
坏了也没人立刻发现（顾客只看到「拍下不付款把库存锁死」）：
- `runScheduledJobs()` 正常 resolve（守护选主超时与模块绑定失效）
- 重复心跳幂等；超时订单被取消且**库存/销量回补**；未超时订单**不**被误伤
- 超时取消**一并回补折扣码**（否则用户券被白吃）
- 清理过期 Refresh Token 与 90 天前审计日志，且保留窗口内的**不**被误删

## 十六、Tailwind 歧义类名：动效可能根本没生效

dev server 启动时告警：

```
warn - The class `duration-[5000ms]` is ambiguous and matches multiple utilities.
warn - The class `ease-[cubic-bezier(0.16,1,0.3,1)]` is ambiguous and matches multiple utilities.
```

`duration-[…]` / `ease-[…]` 在 Tailwind 里是**歧义类名**（`transition-` 与 `animation-`
两个族都可能匹配），构建时告警且**不保证生成预期 CSS** —— 也就是首页分类横幅的
5s 缓慢放大动效可能压根没生效。而 `/collections` 用的是规范的
`[transition-duration:5000ms]`，**同一动效两处写法不一致**。

**修法**：统一为 arbitrary property 写法：
`[transition-duration:5000ms]`、`[transition-timing-function:cubic-bezier(0.16,1,0.3,1)]`。
全库已无其它 `duration-[]` / `ease-[]` / `delay-[]` / `animate-[]` 写法。

### 踩到的坑：Tailwind **会扫描注释文本**

第一次修完，`ease-[cubic-bezier(...)]` 告警**仍在** —— 因为我把类名原文写进了
注释，Tailwind 的候选串提取器连注释一起扫。注释里必须**避开完整的类名字面量**
（本仓库现在写成「duration 的方括号任意值写法」这种描述性措辞）。

### 踩到的坑：`{/* */}` 在 JSX **属性区**是语法错误

我为了「注释更规范」把属性之间的 `//` 换成了 `{/* … */}`，直接 500：

```
Error: Expected '</', got '}'
Parsing ecmascript source code failed   → ./src/app/(shop)/page.tsx:94
```

`{/* */}` 只在**子元素位置**合法；JSX **开标签的属性之间**只能用 `//` 或 `/* */`
（JS 注释），因为属性列表按 JS 语法解析。

**教训**：改完 JSX 必须**立刻**做语法校验，别等页面 500。esbuild 单文件校验很快：

```js
require('esbuild').transformSync(src, { loader: 'tsx', jsx: 'automatic' })
```

注意 `tsc --noEmit` 要跑 4~5 分钟、`next dev` 的报错要等编译，都不适合做即时反馈；
esbuild 单文件 transform 是毫秒级的，改完 JSX 先过这一关。

## 十八、bcrypt 成本因子写死 → 集成测试钩子超时

全量集成运行时 `coupon-flow` 挂在 `beforeAll`：`Hook timed out in 90000ms`
（整文件 15 项被 skip）。根因是一条**放大器**：

`src/lib/auth/password.ts` 里 `const BCRYPT_ROUNDS = 12;` **写死**。
本机（外置卷）实测 **单次哈希 5.8s**（`password.test.ts` 两个用例跑了
5855ms / 4084ms；正常机器 12 轮约 250ms）。而集成测试**每个文件都要
`login()`**，一次登录就是一次 bcrypt 校验 → 90s 的 hookTimeout 被击穿。

**修法**（同时消掉这个魔数硬编码）：

```ts
function resolveBcryptRounds(): number {
  const raw = Number(process.env.BCRYPT_ROUNDS);
  const rounds = Number.isInteger(raw) && raw >= 4 && raw <= 15 ? raw : 12;
  if (isProduction && rounds < 10) throw new Error(`BCRYPT_ROUNDS=${rounds} 过低…`);
  return rounds;
}
```

- `.env.test` 设 `BCRYPT_ROUNDS=4`（测试只需验证哈希正确性，不验证轮数）
- `.env.example` 补上该变量 + 说明（**代码读了但示例没有 = 运营发现不了**，
  这是本仓库第 2 次踩这条：上次是 `SITE_NAME`）
- **生产低于 10 轮拒绝启动** —— 弱哈希约等于明文，宁可起不来

`password.test.ts` 只断言 `/^\$2[aby]\$/`（版本前缀）与盐不同，
**不依赖轮数**，所以调低安全。

另外给 `coupon-flow` / `cron-jobs` 的 `beforeAll` 显式放宽到 240s
（与 `shop-flow` 的 `it(..., 180_000)` 同一处理）：外置卷上「6 次 DB 往返 +
一次登录」在全量并发时确实会超过默认 90s。**不调全局 `hookTimeout`** ——
那会把真正的挂死也一起放过。

### 一句话教训

**测试环境的密码哈希成本必须可调**。写死 12 轮在快机上无害，
在慢机器上会直接把集成测试拖垮，且症状（钩子超时）指不到真正原因
（看起来像「测试写得太重」，实际是「哈希太慢」）。

### 实测收益

`password.test.ts`：**9940ms → 50ms**；
全量集成套件：**487s → 166s**（降 66%），且从「1 文件失败 + 15 项 skip」
变为 **11 文件 / 69 项全通过**。

## 二十、Reveal 渐进增强缺陷：**SSR 直接把内容藏起来**（用户可见）

**怎么发现的**：做 #2（PLP/collections/cart 几何对齐）时，用 1216 视口量首页，
发现 `All Products` 标题行盒在 y=488，而按 `--home-head-pt: 66px`（横幅底 406 + 66）
应为 472，**差 16px**。没有去改 CSS，而是先量出这条垂直链的每一环：

```
header             0..65
hero section      65..406     ← 横幅底 = 406（aspect 720/404，608 宽 → 341 高）
h2 的父 div       488..521    ← 但它是 Reveal 的包装 div
h2 All Products   488..521    lh=32.5px fs=26px
网格              555..4716   ← 555 = 472+33+50，说明布局盒确实是 472
```

网格落在 555 恰好等于「472 + 33 + 50」，反证 **h2 的布局盒是 472..505、CSS 完全正确**，
那 16px 是**视觉位移**——`translate-y-4` 正好 16px，来自 `Reveal` 的入场初始态。

**根因（两条证据链）**：

1. 运行时实测（静止 4s、滚到底都不变）：
   `top=488 h=33 opacity=0 shown=false transform=matrix(1,0,0,1,0,16)`
2. 在页面内**自建一个同参数的 IntersectionObserver** 观察同一元素 → 立刻触发
   `isIntersecting: true, ratio: 1, rootBounds 0..860`。
   → 观察器参数没问题、元素确实可见，是**组件自己的 effect 从未 observe**。
3. 控制台干净、元素带 `__reactFiber$` → hydration 是成功的。

结论：`Reveal` 用 `useEffect([])` 读 `ref.current`，一旦该时机拿不到节点就提前 return、
永不观察；而 **SSR 输出的初始态就是 `translate-y-4 opacity-0`**，于是内容永久隐形。

**关键判断：这不只是开发环境的偶发**。直接抓 SSR HTML（不跑 JS）验证：

```
<div class="transition-[opacity,transform] duration-700 [...] will-change-transform translate-y-4 opacity-0"
```

即 **JS 被禁用 / 加载失败 / 加载缓慢时，首页唯一的可见标题就是隐形的**，
且页面里**没有 `<noscript>` 兜底**。这是渐进增强缺陷，与开发环境无关。

**修法**（保留全部动效参数：16px 位移、700ms、原缓动曲线）：
SSR 与首帧一律**可见**（`idle` → `translate-y-0 opacity-100`）；
客户端挂载后用 `useLayoutEffect`（避免闪一下）测量，**只有确认元素在首屏之外**才切到
`hidden` 并 observe，进入视口后 `shown`。不支持 IntersectionObserver 时保持可见。
→ 无 JS 可见 ✓；首屏内不做无谓入场延迟 ✓；首屏外照常滚动入场 ✓。

**验证**：
- SSR HTML 变为 `translate-y-0 opacity-100` ✓
- 运行时 h2 回到 **y=472**（正确布局位置）且 `opacity: 1` ✓
- 新增 `tests/unit/reveal-ssr.test.ts`（7 条，用 `renderToStaticMarkup`，无需浏览器/DB）
  锁死「SSR 不得输出隐藏态」这一不变量

**教训**：一个「SSR 先藏、客户端再显示」的入场动画 = 把内容可见性押在 JS 上。
正确顺序永远是**默认可见，由客户端按需隐藏**。

## 二十九、资金链路缺陷已修：支付回调**核对金额 + 币种**

**缺陷**：`/api/pay/notify/[channelCode]` 只用了 `VerifyNotifyResult` 的
`orderNumber` / `transactionId`，**把 `amount` 丢掉了**（而它是**必填**字段，
alipay/bankcard 都从已验签报文里提取了它）。
后果：验签只证明「报文来自网关」，不证明「收到的钱等于应付金额」，
签名合法但金额不符的回调会把订单直接置为 PAID = **按应收记账、按实收收款**。

**修复**（`src/app/api/pay/notify/[channelCode]/route.ts`）：
1. 币种守卫：`provider.supportedCurrencies` 声明了支持币种时，订单币种必须在其内
   （跨币种比数值是错的：100 USD ≠ 100 CNY）。**必须在比金额之前拦下**。
2. 金额守卫：两侧都换算成**整数分**后**精确比较**，不等即 `replyFail` 且不推进状态。

**踩到的浮点坑（重要，别重犯）**：第一版写「元为单位、容差 0.01」，
而 `90.01 - 90 === 0.010000000000005116`，在 IEEE754 下**大于** 0.01
→ 「刚好差 1 分」被判成超容差。根因不是容差小，而是**用浮点减法做金额判据**；
把容差调大又会把「接受 1 分以内差额」这个含混语义引进资金链路。
改整数分比较后这类误判从根上消失。另外路由里原本自己定义了
一个与 `@/lib/utils` **同名但语义不同**的 `toCents`（返回元），已删除并改用共享版。

**测试**：新建 `tests/integration/payment-notify.test.ts`（**11 个用例，全绿**），
这是这条链路**首次**有测试。用真实 RSA 密钥对（`generateKeyPairSync` 2048），
签名由被测代码自己的 `signWithRsa` + `buildAlipaySignContent` 生成，
公钥写进渠道加密配置 → 验签走与生产完全相同的路径。覆盖：
验签通过+金额一致→PAID 且应答 `success`；签名篡改→400 且仍 PENDING；
无签名→400；**少付→拒**；**多付→拒**；**差 1 分→拒**；重复回调幂等
（`paidAt` 不被覆盖 + 只有 1 条 `paid` 流水）；USD 订单收到支付宝回调→拒；
订单不存在→400（不能 500，否则网关无限重试）；渠道停用→400；渠道不存在→404。

**测试写法上的两个坑**：
- 建单接口有防刷单限流 `order-create:<userId>` = **5 单/600s**，
  而本文件要建 9 张单 → 第 6 个用例起全是 429。
  解法：建单前调生产代码导出的 `resetRateLimit(\`order-create:${userId}\`)`，
  **不放宽阈值**（限流行为由 `tests/unit/rate-limit.test.ts` 覆盖）。
- 测试环境订单币种是 **CNY**（`.env.test` 的 `CURRENCY=CNY`），
  不是原先假设的 USD → 币种用例必须**显式**构造 USD 订单，不能依赖环境默认值。
